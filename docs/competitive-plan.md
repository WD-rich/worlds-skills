# 超越基准产品的实现计划

> 当前执行策略：P3 十倍规模暂缓，先在 P0/P1 的小规模世界上把截图级舞台、确定性回放和可观察交互跑通。扩展数据可以保留，但不作为默认入口，也不以规模掩盖体验缺口。

## 目标

目标不是复刻一个截图，而是交付一个从一句话到可观察、可干预、可回放世界的完整产品。视觉上达到截图所示的层级，运行上具备更强的确定性、解释性、可替换性和规模控制。

基准体验包含六个用户可感知的部分：

1. 一句话创建世界；
2. 与设定一致的地图和角色资产；
3. 角色自主移动、交互和对话；
4. 记忆、人格、关系和多日演化；
5. 地图、角色面板、事件流和时间线；
6. 上帝干预、沙盒对话和多时间线。

我们的交付必须覆盖这六部分，并额外提供：

- 每次行动都有来源、规则、前后状态和回放信息；
- Codex、规则模型、本地模型和 HTTP Provider 可以互换；
- 图片、视觉审查或模型失败时，世界仍能用程序化资源继续运行；
- 分支可以比较，决定可以解释，成本和延迟可以观察；
- 工作区可以导出、恢复、迁移和脱离服务运行。

## 本轮重建原则

现有实现可以整体替换，世界事实和回放记录只有在明确选择“视觉重做”时才保留。所有新视觉工作先经过 `world-production-director`：选择 `cinematic-2.5d` 或 `pixel-sim`，列出能力缺口，创建小规模 hero slice，分别通过结构、运行、交互和人工视觉评审。这样同一套 Skill 能服务不同世界，也能在未来加入新的视觉 profile，而不会把 Ashfall 的临时 CSS、占位角色或单张概念图写死为产品标准。

两套 profile 的职责不同：`cinematic-2.5d` 追求截图参考中的完整场景、统一三分之四相机、地图主视野、角色上下文卡和底部时间线；`pixel-sim` 追求固定内部画布、整数缩放、瓦片导航、逐帧角色动作和紧凑 HUD。它们共享世界数据、回放、来源和审计，不共享未经声明的布局假设。

## 产品形态

### 创建页

用户输入一句话后，先看到可编辑的世界草案：世界名、视觉风格、空间、角色、资源、时间规则、内容边界和预计成本。用户可选择 1K/2K/4K 规模，但规模只影响预算和细节，不改变契约。

创建流程分为可观察的作业阶段：`设计 → 空间 → 角色 → 地图资产 → 角色资产 → 初始快照 → 审计`。每阶段都能重试、取消、继续和查看产物，失败只降级该阶段，不丢失已经成功的产物。

### 世界舞台

舞台采用“地图 + 信息层”结构：

- 顶部：世界、时间线、当前时间、运行/回放/暂停、新时间线、新世界；
- 中央：俯视地图、区域、可行走路径、角色动画、交互锚点、对话气泡；
- 左下：缩略图、缩放、镜头定位和当前视野；
- 右侧：角色列表、选中角色详情、需求/情绪/库存/关系、历史和记忆；
- 底部：当前对话、事件流、推进一步、播放速度和回放进度；
- 上帝工具：广播、私语、编辑允许字段、提交干预、沙盒聊天。

舞台必须支持 `live`、`replay`、`sandbox` 三种明确模式。视觉组件只能消费快照和事件，不能直接编辑运行文件。

### 世界内核

内核采用事件溯源：

```text
observe → perceive → propose → validate → apply → remember → narrate → record
```

模型只提供候选内容或意图。内核负责时间、占用、容量、资源、关系、能力、动作持续时间、状态迁移、事件追加、快照和回放。

## Skill 到实现模块

| 产品能力 | Skill | 必须实现的模块 | 验收结果 |
| --- | --- | --- | --- |

| 一句话世界设计 | `world-conceiver` | 结构化世界草案、规则和边界 | 相同种子生成同一份草案 |
| 契约和迁移 | `contract-keeper` | Schema、ID、迁移、结果封装 | 旧工作区能被诊断或迁移 |
| 模型接入 | `model-bridge` | Codex、规则、HTTP、本地 Provider、成本记录 | Provider 可替换且不改内核 |
| 空间和导航 | `atlas-builder` | 图、区域、容量、路径、交互点 | 图连通、邻接双向、路径可验证 |
| 地图资产 | `scene-painter` | 基图、区域图层、可行走 mask、网格、视觉审查 | 有图时更好看，无图时仍可运行 |
| 角色设定 | `cast-forger` | profile/state/关系/库存 | 每个角色可执行、可观察、可定位 |

| 素材生产图 | `asset-pipeline-director` | 多步骤素材编排、结果导入、预算、哈希、回退和预览 | 同一份素材图可离线复跑，Provider 可替换 |
| 感知和行动 | `agent-cognition` | 可见上下文、需求、情绪、行动菜单 | 不泄露隐藏信息，意图可解释 |
| 时间步 | `life-director` | 调度、状态迁移、日夜循环 | 事件可回放，非法动作被拒绝 |
| 对话 | `dialogue-director` | 会话、回合、关系/情绪/记忆影响 | 正式对话与沙盒隔离 |
| 记忆 | `memory-weaver` | 检索、重要性、衰减、反思、日记 | 记忆有来源且不改写事实 |
| 时间线 | `timeline-keeper` | 分支、切换、比较、恢复 | 分支从快照开始，事件流不混写 |
| 剧情内容 | `story-chronicler` | 摘要、名句、精彩事件、评分 | 所有内容可追溯到记录 |
| 上帝操作 | `world-console` | 查询、广播、私语、编辑、沙盒 | 每个变更都有审计事件 |
| 可视化舞台 | `world-stage` | Phaser/Canvas 场景、React 面板、回放控制 | 40 角色下仍可操作 |
| 作业运行 | `world-runner` | 创建、进度、取消、恢复、清理 | 失败不损坏源工作区 |
| 质量保证 | `world-audit` | 契约、资产、回放、成本和安全检查 | CI 可以阻止坏世界进入舞台 |
| 视觉验收 | `stage-visual-qa` | 真实截图、交互状态、profile 评审、人审记录 | 技术通过与视觉通过分开记录 |

## 分阶段交付

### P0：小世界垂直切片

范围：6 个空间、4 个角色、5 个时间步。

- 一句话或固定种子生成结构化世界；
- 角色可移动、交换资源、发出信号并形成一段正式对话；
- 写入至少一条带来源的记忆和一条摘要；
- 从 `snapshot-000` 回放到最终快照，哈希一致；
- 使用程序化地图和角色占位图即可展示。

通过标准：`world-check` 审计通过，事件缺字段或状态漏记时必须失败。

### P1：截图级视觉垂直切片

范围：沿用 P0 世界，加入一个完整地图场景和 4 个可识别角色。

- 顶部控制栏、中央地图、右侧角色面板、底部对话条和左下缩略图齐全；
- 角色有方向、待机、移动三种状态；
- 地图可缩放、拖拽、定位，角色移动由事件驱动；
- 对话气泡来自 `DialogueSession`，点击角色可查看历史/记忆；
- 同一世界可在 live/replay 间切换。

通过标准：静态资源缺失时仍能运行；刷新后从工作区恢复；UI 不直接改写状态文件。

### P2：创建和运行产品化

- 创建页显示阶段、进度、重试、取消和成本；
- `model-bridge` 支持 Codex 为主 Provider，规则 Provider 为离线 fallback；
- 地图和角色资产支持生成、审查、替换和版本化；
- 支持中英文文案和无障碍文本层；
- 运行状态、Provider 失败、资源缺失和回放错误都可见。
- 素材工作流能输出版本化包和 HTML 预览，在线 Provider 缺失时不阻塞舞台。

### P3：十倍规模运行

范围：60 个空间、40 个角色、50 个时间步，并增加跨区域关系和多日阶段。

- 地图按 region 聚合加载，角色和事件按视野/时间窗口订阅；
- 运行时不把每个模型调用绑定到每个画面帧；
- 快照、事件日志和记忆索引可断点续跑；
- 10/20/30/40/50 步快照都能回放和比较；
- Stage 在目标规模下保持可交互，数据层可独立无头运行。

### P4：超过基准产品的能力

- **可解释行动**：显示角色看到了什么、缺什么、为何选择该动作、哪些候选被拒绝；
- **时间旅行调试**：对任意分支查看状态差异、资源差异和关系变化；
- **Provider 竞赛**：同一世界用规则、Codex、本地模型运行并比较质量、成本和延迟；
- **视觉一致性**：世界级风格锁、角色级外观锚点、地图/角色审查分数和回退策略；
- **可移植世界包**：导出后可在没有外部 API 的情况下查看、回放和审计；
- **开放扩展**：资源、规则、Provider、舞台面板和叙事器都可作为插件加入。

## 质量门槛

每个阶段都必须同时通过四类检查：

1. **结构**：Schema、ID、引用、容量、资源和资产映射完整；
2. **运行**：非法动作被拒绝，事件追加，快照可恢复；
3. **回放**：同一种子和事件前缀得到相同哈希；
4. **体验**：用户可以看懂当前世界、角色正在做什么，以及下一步能做什么。

只有 P0 通过，才扩展到 P1；只有 P1 通过，才扩展到 P3。规模增加不能掩盖舞台和内核的缺陷。

## 当前执行顺序

1. 把 P0 从当前确定性工作区提炼成真正的 `world-runner` 命令，而不是手工准备记录；
2. 在 `neo_world` 完成 P1 的独立舞台，先用可替换的原创像素风资源；
3. 用小规模工作区验证角色点击、对话、时间轴、回放、沙盒和上帝视角入口；
4. 接入 `scene-painter` 和 `sprite-forger` 的可选 Provider，再完成 P2 的创建作业和 Codex Provider；
5. **暂停**对 60/40/50 工作区的 P3 压测、回放和舞台加载，直到 P1 体验验收完成；
6. 以 P4 的解释性、时间旅行和可移植包作为超越基准的长期差异。
